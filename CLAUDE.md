# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`github.com/elojah/broadcastor` is a Go library (package `broadcastor` at the root, no `cmd/`, plus runnable programs under `examples/` and helper packages under `pkg/`) that provides a generic in-process fan-out: one `Broadcast` call hands a message to every subscriber's `handle` function. Its only dependency is `github.com/google/uuid`. `go.mod` requires Go 1.26.1.

## Commands

```sh
go build ./...
go vet ./...
go test -race ./...                 # always use -race, the package is all concurrency
go test -race -run TestName ./...   # run a single test
make check                          # golangci-lint + tests
make bench                          # benchmarks (BenchmarkBroadcast: subscriber counts × sync/async/buffered)
```

Lint uses the committed `.golangci.yml`: `default: all` minus a disable list, the same config as the author's other repos. So `nlreturn` (blank line before `return`), `paralleltest` (`t.Parallel()` first in every test), `forcetypeassert`, `err113` and `godot` apply to tests too. CI (`.github/workflows/ci.yml`) installs a pinned golangci-lint into `./bin`, which the Makefile picks up, and runs `make check`.

## Architecture

- `Broadcastor[T]` (`broadcastor.go`) keeps subscribers in a `sync.Map` from a `uuid.UUID` (v7) to a `*subscriber[T]` (`subscriber.go`), which holds a `chan message[T]` (**unbuffered** unless `WithSubscriberBuffer`), an atomic reference count and a `subscriberConfig`.
  - `Subscribe(ctx, handle, options...)` returns the subscriber's ID and starts its goroutine (`consume`), which calls `handle(ctx, msg)` for each message on the channel until it is closed. `ctx` is the one passed to `Subscribe`. Cancelling it does not end the subscription, unless `WithSubscriberAutoUnsubscribe` (see below). Both subscribe paths create and store the subscriber through `add`.
  - `SubscribeSeq(ctx, options...)` returns the ID and an `iter.Seq[T]` instead of taking a `handle`, and starts no goroutine: ranging over it reads the channel directly (`subscriber.pull`), so the loop body plays `handle` exactly (buffer, non-blocking and ordering behave the same, with no extra hop). The loop ends on `break`/return/panic, on `ctx` done (checked before every receive, so a done ctx yields nothing more), or when the channel is closed after an outside `Unsubscribe`. On the way out it calls `Unsubscribe` (ignoring not-found) and starts `go subscriber.discard`, which reads the channel until `release` closes it and reports each message as a `*SubscriberClosedError` with the `SubscribeSeq` ctx. The discard is a goroutine and not inline, because a `send` releases its reference only after calling the user's error handler, which may be waiting on the ranging goroutine. An `atomic.Bool` makes the iterator single-use: any other range, concurrent or later, yields nothing (a second reader would steal from the loop or the discard). Until the loop starts nothing reads the channel, so `Broadcast` waits for it as for a busy `handle`.
  - `Broadcast(ctx, msg, options...)` goes through the subscribers one at a time and sends `msg` to each one. A subscriber only reads its next message once `handle` returns, so a slow subscriber holds up delivery to all subscribers after it. Once `ctx` is done, `Broadcast` stops waiting: the current subscriber misses the message, and so may every later one (`select` picks at random between sending and giving up). A message's timeout (`WithMessageTimeout`, defaulting to `WithSubscriberTimeout`) also makes `Broadcast` stop waiting, but it is counted separately for each subscriber, from when `Broadcast` gets to it. `send` derives the timeout ctx itself and still passes the `Broadcast` ctx to the error handlers. With `WithMessageAsync`, `Broadcast` takes a reference on every subscriber (`acquire`) and returns right away, and each send runs in its own goroutine under the same `ctx`. A slow subscriber then holds up nobody else, but messages from successive async `Broadcast`s can reach a subscriber out of order. With `WithMessageNonBlocking`, `send` does a `select` with `default`: the subscriber takes the message only if it is idle (unbuffered) or has room in its buffer, and otherwise misses it with a `*DroppedError[T]`. ctx and timeouts play no part. `Broadcast` returns how many subscribers it handed the message to: sync and non-blocking sends that were taken (`send` returns whether it was), plus every async send it started.
- **Errors from `handle`**: if the subscriber was given `WithSubscriberErrorHandler`, each error is passed to the handler as a `*HandleError[T]` (subscriber ID, message, wrapped error), with the `Subscribe` ctx. The handler runs in the subscriber's goroutine right after `handle`, so a slow handler holds things up just like a slow `handle`. A message can also carry its own handler (`WithMessageErrorHandler`). Every error about that message then goes to **both** handlers, the subscriber's first (`subscriber.report`, the only place handlers are called; each one may be nil). A message handler is shared by every subscriber of a `Broadcast`, so it can be called concurrently and after `Broadcast` returns. With `WithSubscriberRecover`, a panic in `handle` is recovered in `subscriber.process` and reported the same way as a `*PanicError[T]` (panic value and stack), and the subscriber goes on consuming. `report` runs outside that recover, so a panic in an error handler still crashes. When `Broadcast` can't hand a message over, it reports a `*TimeoutError[T]` (ctx done), a `*DroppedError[T]` (non-blocking, subscriber busy) or a `*SubscriberClosedError[T]` (unsubscribed since `Range` picked it up), with the `Broadcast` ctx. `*SubscriberClosedError[T]` is also what `discard` reports for messages a `SubscribeSeq` loop took but never yielded. Without a handler, errors are discarded. They used to go to a channel returned by `Subscribe`. That was removed because an unread error blocked the subscriber, which then blocked `Broadcast` (see `TestSubscribe_ErrorsWithoutHandler`). Don't bring back an error path the library owns that blocks when nobody reads it. Blocking is only acceptable inside the user's own handler.
- **Closing by reference count**: the subscription itself holds one reference, and each `Broadcast` takes one (`acquire`) for as long as it sends to that subscriber. `Unsubscribe` removes the subscriber from the map and drops the subscription's reference (`release`). Whoever drops the count to 0 closes the channel. So the channel is closed right away if no `Broadcast` is sending to it, or else by the last such `Broadcast` once it is done. The subscriber's goroutine keeps processing until the channel is closed, so it can still get a message after `Unsubscribe` returns. Two rules keep this safe, and any change to how channels are closed or removed has to preserve them:
  - Only `release` closes a channel, and `acquire` refuses a count that is already 0, so a `Broadcast` that picked the subscriber up from `Range` just before it was unsubscribed skips it instead of sending on a closed channel.
  - Neither `Unsubscribe` nor `Broadcast` ever waits for another `Broadcast`. `handle` often calls `Unsubscribe` itself, and the subscriber is not reading at that point, so any such wait can deadlock (see `TestUnsubscribe_SelfDuringBroadcast` and `TestUnsubscribe_SeveralThenDrain`).
- **`Close()`** unsubscribes everyone and refuses new subscribers. It closes `gate` (a `gate.Gate` from `pkg/gate`: an `RWMutex` and a `closed` bool behind `Enter`/`Leave`/`Close`), then goes through the map and removes every subscriber with `remove`. `remove` is the `LoadAndDelete` + `release` that `Unsubscribe` also uses, so when `Unsubscribe` and `Close` race on one subscriber, only the one that deleted it drops the subscription's reference. `add` stores the subscriber between `gate.Enter` and `gate.Leave`, and `gate.Close` waits for every `Leave`, so every subscriber is either refused with `ErrClosed` or stored before `Close` goes through the map. Every `Close` goes through the map, not just the first, so that no subscriber is left once any `Close` returns. `Broadcast` does not use `gate`: after `Close` the map is empty, so it returns 0. `Close` follows the same rule as `Unsubscribe` and never waits, so `handle` can call it (see `TestClose_FromHandle`). `TestClose_Parallel` stops its broadcaster before waiting for the subscribers: a goroutine that never blocks keeps the synctest clock from advancing, so a leaked subscriber would otherwise hang the test instead of failing it.
- **Discarding on unsubscribe** (`WithUnsubscribeDiscard`): `remove` builds an `unsubscription` from `subscriber.config.unsubscribeDefaults` (set by `WithSubscriberDefaultUnsubscribeOptions`) and then the `Unsubscribe`'s options (`Close` passes none, so it applies only the defaults). If it says discard, `remove` sets `subscriber.discarding` **before** `release`, since `release` may close the channel right away and the reader must see the flag for every buffered message. The subscriber's existing reader does the discarding, never a second one (it would steal messages): `consume` reports each message it takes as a `*SubscriberClosedError` instead of calling `handle`, until the channel is closed, and `pull` stops (it checks before each receive, and after, reporting the one it got), so the loop ends and its `go discard` reports the rest. Nothing waits, so `handle` (or the loop body) can still start for the one message whose check came just before the flag was set. Only whoever deletes the subscriber from the map applies its options, so an `Unsubscribe(..., WithUnsubscribeDiscard())` that loses a race to a plain `Close` returns not-found and the messages are handled. `UnsubscribeOption` is not generic, so call sites need no `[T]`. `WithUnsubscribeDeliver` is the default and only overrides a subscriber's default. Tests are in `unsubscribe_discard_test.go`.
- **Auto-unsubscribe** (`WithSubscriberAutoUnsubscribe`): `add` registers `context.AfterFunc(ctx, remove)` on the `Subscribe`/`SubscribeSeq` ctx **before** storing the subscriber, so its stop func (`subscriber.autoRemove`) is set by the time anyone can remove it. `unsubscribe` calls it however the subscriber was removed, so nothing waits on a ctx that may never be done. `TestWithSubscriberAutoUnsubscribe_NoLeak` uses a ctx type the context package does not know, for which `AfterFunc` starts a goroutine, so a missing stop leaks it and fails the synctest test. When ctx is already done, the callback may run before `Store` and find nothing, so `add` checks `ctx.Err()` again after `Store`. Every removal goes through `remove`, so exactly one of them (or a racing `Unsubscribe`/`Close`) applies the subscriber's unsubscribe defaults. Like `Unsubscribe`, it never waits, so it unsubscribes even while `handle` or the loop body is running. Tests are in `auto_unsubscribe_test.go`.
- Options (`options.go`): `SubscriberOption[T]` (`WithSubscriberBuffer`, `WithSubscriberErrorHandler`, `WithSubscriberRecover`, `WithSubscriberAutoUnsubscribe`, `WithSubscriberDefaultMessageOptions`, `WithSubscriberDefaultUnsubscribeOptions`, `WithSubscriberTimeout`) is applied in `add` to a `subscriberConfig`, which `add` then builds the subscriber from (`buffer` sizes the channel). Options change only that config, never the subscriber itself: `id`, `ch`, `discarding`, `autoRemove` and `refs` are set by the library. `UnsubscribeOption` (`WithUnsubscribeDiscard`, `WithUnsubscribeDeliver`) is applied in `remove`, see above. `WithSubscriberRecover` does nothing for `SubscribeSeq`, whose loop body runs in the caller's goroutine. `MessageOptions[T]` (`WithMessageSync`, `WithMessageAsync`, `WithMessageNonBlocking`, `WithMessageErrorHandler`, `WithMessageTimeout`) set up the `messageConfig` (`message.go`) of the `message[T]` (value + config) that a single `Broadcast` sends to one subscriber. That config is built **per subscriber** by `newMessage`: first a copy of `subscriber.config.defaults` (filled in once by `WithSubscriberDefaultMessageOptions`), then the `Broadcast`'s options, which override it. Neither config needs `T`, so `SubscriberOption[T]` and `MessageOptions[T]` keep their type parameter only for the public API. Sync, async and non-blocking are a single `messageConfig.delivery` enum (`deliverySync` is the zero value), so the last of those options wins. A subscriber whose default is `WithMessageAsync` or `WithMessageNonBlocking` is never waited for, unless a `Broadcast` passes `WithMessageSync`. `WithSubscriberTimeout(d)` is just shorthand for a default `WithMessageTimeout(d)`, so a `Broadcast`'s own timeout replaces it (0 means none). The `ctx` of `Unsubscribe` is unused.
- Errors are typed structs in `errors.go` (`*SubscriberNotFoundError`, `*HandleError[T]`, `*PanicError[T]`, `*TimeoutError[T]`, `*DroppedError[T]`, `*SubscriberClosedError[T]`), each with an exported `SubscriberID`. Every type the library creates (all but `HandleError`, which wraps the user's error) has an `Is` method matching one sentinel (`ErrSubscriberNotFound`, `ErrPanic`, `ErrTimeout`, `ErrDropped`, `ErrSubscriberClosed`), so callers can use `errors.Is` without knowing `T`. `TimeoutError` also unwraps to the ctx error, and `PanicError` to the panic value when that is an error. `ErrClosed` has no type: `Subscribe`, `SubscribeSeq` and every `Close` after the first return it as is.

## Tests

Most tests run inside a `synctest` bubble. There, a subscriber goroutine that never ends (because its channel was never closed, or because it is stuck) fails the test, and `synctest.Wait()` after `Unsubscribe` waits until the subscriber has processed everything. Every wait is bounded by `deadlockTimeout`, so a deadlock fails the test instead of hanging. `pkg/gate`'s tests run in real time instead: a goroutine blocked on a `sync.RWMutex` is not durably blocked, so `synctest.Wait()` would hang while `Close` waits for `Leave`.

The examples (`examples/NN-name/main.go`, numbered from simple to complex, listed in the README) are `main` programs, each with a `main_test.go` whose `Example()` runs `main()` and checks its output. They run in real time, not in a bubble, so their output must not depend on scheduling: they synchronise on channels or a `WaitGroup`, or use `// Unordered output:`. A slow `handle` waits on a `release` channel rather than sleeping. `forbidigo` is excluded for `examples/` in `.golangci.yml`, since they print. `bench_test.go` holds the benchmarks. Each `BenchmarkBroadcast` op waits until every subscriber has handled the message, which keeps async from piling up goroutines.
