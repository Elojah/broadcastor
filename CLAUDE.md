# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`github.com/elojah/broadcastor` is a Go library (package `broadcastor` at the root, no `cmd/`, plus the subscriber side in `subscriber/`, the message side in `message/`, ready-made middlewares in `middleware/`, runnable programs under `examples/` and helper packages under `pkg/`) that provides a generic in-process fan-out: one `Broadcast` call hands a message to every subscriber's `handle` function. Its only dependency is `github.com/google/uuid`. `go.mod` requires Go 1.26.1.

## Commands

```sh
go build ./...
go vet ./...
go test -race ./...                 # always use -race, the package is all concurrency
go test -race -run TestName ./...   # run a single test
make check                          # golangci-lint + tests
make bench                          # benchmarks (BenchmarkBroadcast: subscriber counts × sync/parallel/async/buffered/middleware)
```

Lint uses the committed `.golangci.yml`: `default: all` minus a disable list, the same config as the author's other repos. So `nlreturn` (blank line before `return`), `paralleltest` (`t.Parallel()` first in every test), `forcetypeassert`, `err113` and `godot` apply to tests too. `funcorder` wants exported methods before unexported ones. CI (`.github/workflows/ci.yml`) installs a pinned golangci-lint into `./bin`, which the Makefile picks up, and runs `make check`.

## Architecture

- **Packages**: `broadcastor` (root) holds `Broadcastor[T]`, `ErrClosed` and `SubscriberNotFoundError`. `subscriber` holds `Subscriber[T]`, the options passed to `Subscribe`, `SubscribeSeq` and `Unsubscribe` (`Option[T]`, `UnsubscribeOption`), `Handler`/`Middleware`, and every error about a subscriber's messages. `message` holds `Message[T]`, `Config`, `Delivery` and the options passed to `Broadcast` (`Option[T]`). Imports go one way: `broadcastor` → `subscriber` → `message`, and `middleware` → `subscriber` (not `broadcastor`). Options carry no `WithSubscriber`/`WithMessage` prefix, since the package name says it (`subscriber.WithBuffer`, `message.WithAsync`). `Subscriber[T]` exports only what `Broadcastor` calls: `New`, `ID`, `AutoUnsubscribe`, `Deliver`, `Unsubscribe`, `Consume` and `Seq`. The reference counting (`acquire`, `release`, `send`), `report`, `pull` and `discard` stay unexported, so the closing rules below hold inside `subscriber` whatever a caller does.
- `Broadcastor[T]` (`broadcastor.go`) keeps subscribers in a `sync.Map` from a `uuid.UUID` (v7) to a `*subscriber.Subscriber[T]` (`subscriber/subscriber.go`), which holds a `chan message.Message[T]` (**unbuffered** unless `subscriber.WithBuffer`), an atomic reference count and its `config`.
  - `Subscribe(ctx, handle, options...)` returns the subscriber's ID and starts its goroutine (`Consume`), which calls `handle(ctx, id, msg)`, wrapped in its middlewares, for each message on the channel until it is closed. `id` is the subscriber's own, so `handle` can unsubscribe itself without capturing the ID `Subscribe` returns (which would race with a `Broadcast` from another goroutine). `ctx` is the one passed to `Subscribe`. Cancelling it does not end the subscription, unless `subscriber.WithAutoUnsubscribe` (see below). Both subscribe paths create and store the subscriber through `add`.
  - `SubscribeSeq(ctx, options...)` returns the ID and the `iter.Seq[T]` from `Subscriber.Seq` instead of taking a `handle`, and starts no goroutine: ranging over it reads the channel directly (`pull`), so the loop body plays `handle` exactly (buffer, non-blocking and ordering behave the same, with no extra hop). The loop ends on `break`/return/panic, on `ctx` done (checked before every receive, so a done ctx yields nothing more), or when the channel is closed after an outside `Unsubscribe`. On the way out it calls the `unsubscribe` func `SubscribeSeq` passed to `Seq` (`b.remove`, ignoring not-found) and starts `go discard`, which reads the channel until `release` closes it and reports each message as a `*subscriber.ClosedError` with the `SubscribeSeq` ctx. The discard is a goroutine and not inline, because a `send` releases its reference only after calling the user's error handler, which may be waiting on the ranging goroutine. An `atomic.Bool` makes the iterator single-use: any other range, concurrent or later, yields nothing (a second reader would steal from the loop or the discard). Until the loop starts nothing reads the channel, so `Broadcast` waits for it as for a busy `handle`.
  - `Broadcast(ctx, msg, options...)` goes through the subscribers one at a time and calls `Subscriber.Deliver` on each, which takes a reference (`acquire`) and sends `msg`. A subscriber only reads its next message once `handle` returns, so a slow subscriber holds up delivery to all subscribers after it. Once `ctx` is done, `Broadcast` stops waiting: the current subscriber misses the message, and so may every later one (`select` picks at random between sending and giving up). A message's timeout (`message.WithTimeout`, defaulting to `subscriber.WithTimeout`) also makes `Broadcast` stop waiting, but it is counted separately for each subscriber, from when `Broadcast` gets to it. `send` derives the timeout ctx itself and still passes the `Broadcast` ctx to the error handlers. With `message.WithAsync`, `Deliver` runs `send` in its own goroutine under the same `ctx` and returns right away. A slow subscriber then holds up nobody else, but messages from successive async `Broadcast`s can reach a subscriber out of order. With `message.WithParallel`, `Deliver` also runs `send` in its own goroutine, but returns a buffered `chan bool` that yields whether the subscriber took the message, and `Broadcast` waits on each of them once `Range` is done. A slow subscriber then holds up only `Broadcast`, successive `Broadcast`s from one goroutine stay in order, and the ctx deadline and the timeout run from the same moment for every subscriber. Each send gives up like a sync one, so this never waits for another `Broadcast`. A sync subscriber in the same `Broadcast` still delays the parallel sends `Range` gets to after it. `pending` stays nil without a parallel send, so the other modes allocate nothing more. With `message.WithNonBlocking`, `send` does a `select` with `default`: the subscriber takes the message only if it is idle (unbuffered) or has room in its buffer, and otherwise misses it with a `*subscriber.DroppedError[T]`. ctx and timeouts play no part. `Broadcast` returns how many subscribers it handed the message to: sync and non-blocking sends that were taken (`send` returns whether it was), plus every async send it started (`Deliver` returns true for those), plus parallel sends that were taken (read from the channels).
- **Errors from `handle`**: if the subscriber was given `subscriber.WithErrorHandler`, each error is passed to the handler as the handler chain returned it (a `*subscriber.HandleError[T]` with subscriber ID, message and wrapped error only with `middleware.WrapError`), with the `Subscribe` ctx. The handler runs in the subscriber's goroutine right after `handle`, so a slow handler holds things up just like a slow `handle`. A message can also carry its own handler (`message.WithErrorHandler`). Every error about that message then goes to **both** handlers, the subscriber's first (`Subscriber.report`, the only place handlers are called; each one may be nil). A message handler is shared by every subscriber of a `Broadcast`, so it can be called concurrently and after `Broadcast` returns. With `middleware.Recover`, a panic in `handle` or a later middleware is returned as a `*subscriber.PanicError[T]` (panic value and stack) and reported the same way, and the subscriber goes on consuming. `report` runs outside the chain (it is called from `Consume`), so a panic in an error handler still crashes. When `Deliver` can't hand a message over, it reports a `*subscriber.TimeoutError[T]` (ctx done), a `*subscriber.DroppedError[T]` (non-blocking, subscriber busy) or a `*subscriber.ClosedError[T]` (unsubscribed since `Range` picked it up), with the `Broadcast` ctx. `*subscriber.ClosedError[T]` is also what `discard` reports for messages a `SubscribeSeq` loop took but never yielded. Without a handler, errors are discarded. They used to go to a channel returned by `Subscribe`. That was removed because an unread error blocked the subscriber, which then blocked `Broadcast` (see `TestSubscribe_ErrorsWithoutHandler`). Don't bring back an error path the library owns that blocks when nobody reads it. Blocking is only acceptable inside the user's own handler.
- **Closing by reference count**: the subscription itself holds one reference, and each `Broadcast` takes one (`acquire`, in `Deliver`) for as long as it sends to that subscriber. `Unsubscribe` removes the subscriber from the map and drops the subscription's reference (`Subscriber.Unsubscribe`, which calls `release`). Whoever drops the count to 0 closes the channel. So the channel is closed right away if no `Broadcast` is sending to it, or else by the last such `Broadcast` once it is done. The subscriber's goroutine keeps processing until the channel is closed, so it can still get a message after `Unsubscribe` returns. Two rules keep this safe, and any change to how channels are closed or removed has to preserve them:
  - Only `release` closes a channel, and `acquire` refuses a count that is already 0, so a `Broadcast` that picked the subscriber up from `Range` just before it was unsubscribed skips it (`Deliver` reports a `*subscriber.ClosedError`) instead of sending on a closed channel.
  - Neither `Unsubscribe` nor `Broadcast` ever waits for another `Broadcast`. `handle` often calls `Unsubscribe` itself, and the subscriber is not reading at that point, so any such wait can deadlock (see `TestUnsubscribe_SelfDuringBroadcast` and `TestUnsubscribe_SeveralThenDrain`).
- **`Close()`** unsubscribes everyone and refuses new subscribers. It closes `gate` (a `gate.Gate` from `pkg/gate`: an `RWMutex` and a `closed` bool behind `Enter`/`Leave`/`Close`), then goes through the map and removes every subscriber with `remove`. `remove` is the `LoadAndDelete` + `Subscriber.Unsubscribe` that `Unsubscribe` also uses, so when `Unsubscribe` and `Close` race on one subscriber, only the one that deleted it drops the subscription's reference. `add` stores the subscriber between `gate.Enter` and `gate.Leave`, and `gate.Close` waits for every `Leave`, so every subscriber is either refused with `ErrClosed` or stored before `Close` goes through the map. Every `Close` goes through the map, not just the first, so that no subscriber is left once any `Close` returns. `Broadcast` does not use `gate`: after `Close` the map is empty, so it returns 0. `Close` follows the same rule as `Unsubscribe` and never waits, so `handle` can call it (see `TestClose_FromHandle`). `TestClose_Parallel` stops its broadcaster before waiting for the subscribers: a goroutine that never blocks keeps the synctest clock from advancing, so a leaked subscriber would otherwise hang the test instead of failing it.
- **Discarding on unsubscribe** (`subscriber.WithUnsubscribeDiscard`): `Subscriber.Unsubscribe`, called by `remove`, builds an `unsubscription` from `config.unsubscribeDefaults` (set by `subscriber.WithDefaultUnsubscribeOptions`) and then the `Unsubscribe`'s options (`Close` passes none, so it applies only the defaults). If it says discard, it sets `discarding` **before** `release`, since `release` may close the channel right away and the reader must see the flag for every buffered message. The subscriber's existing reader does the discarding, never a second one (it would steal messages): `Consume` reports each message it takes as a `*subscriber.ClosedError` instead of calling `handle`, until the channel is closed, and `pull` stops (it checks before each receive, and after, reporting the one it got), so the loop ends and its `go discard` reports the rest. Nothing waits, so `handle` (or the loop body) can still start for the one message whose check came just before the flag was set. Only whoever deletes the subscriber from the map applies its options, so an `Unsubscribe(..., subscriber.WithUnsubscribeDiscard())` that loses a race to a plain `Close` returns not-found and the messages are handled. `UnsubscribeOption` is not generic, so call sites need no `[T]`. `subscriber.WithUnsubscribeDeliver` is the default and only overrides a subscriber's default. Tests are in `unsubscribe_discard_test.go`.
- **Auto-unsubscribe** (`subscriber.WithAutoUnsubscribe`): `add` calls `Subscriber.AutoUnsubscribe(ctx, remove)`, which registers `context.AfterFunc(ctx, remove)` on the `Subscribe`/`SubscribeSeq` ctx, **before** storing the subscriber, so its stop func (`stopAutoUnsubscribe`) is set by the time anyone can remove it. `Subscriber.Unsubscribe` calls it however the subscriber was removed, so nothing waits on a ctx that may never be done. `TestSubscriberWithAutoUnsubscribe_NoLeak` uses a ctx type the context package does not know, for which `AfterFunc` starts a goroutine, so a missing stop leaks it and fails the synctest test. When ctx is already done, the callback may run before `Store` and find nothing, so `add` checks `ctx.Err()` again after `Store` (`AutoUnsubscribe` reports whether it registered anything). Every removal goes through `remove`, so exactly one of them (or a racing `Unsubscribe`/`Close`) applies the subscriber's unsubscribe defaults. Like `Unsubscribe`, it never waits, so it unsubscribes even while `handle` or the loop body is running. Tests are in `auto_unsubscribe_test.go`.
- **Middleware** (`subscriber/middleware.go`, `middleware/`): `subscriber.Handler[T]` is `handle`'s signature, `func(ctx, id uuid.UUID, msg T) error`, and `subscriber.Middleware[T]` is `func(next Handler[T]) Handler[T]`. `subscriber.WithMiddleware` appends to `config.middlewares`, and `Consume` wraps `handle` in them once (`chain`: first outermost, nil skipped). The library applies no middleware of its own: errors reach the error handlers as the chain returns them, and a panic in `handle` or a middleware crashes. The `middleware` package (it imports `subscriber`, never the reverse) holds the ready-made ones: `Recover` (panic → `*subscriber.PanicError`, `middleware/recover.go`), `WrapError` (error → `*subscriber.HandleError`, `middleware/wrap_error.go`) and `Retry(RetryPolicy)` (`middleware/retry.go`), each in its own file, with the package doc in `middleware/doc.go`. `Recover` and `WrapError` get the subscriber ID from `handle`'s `id` parameter, which is why it is there. `Retry` calls `next` again after an error, up to `Attempts` calls in all, waiting `Delay`, then each wait times `Multiplier` (≤ 1 keeps it constant), every wait capped at `MaxDelay` and shortened at random by up to `Jitter` (clamped to [0, 1], so it never waits longer than without jitter). It stops at the first error `IsRetryable` rejects, and before any retry once ctx is done, including during a wait (a `time.NewTimer` in a `select` with `ctx.Done()`). The first call is always made. It returns the last error as is. It waits in the subscriber's goroutine, so it holds the subscriber up like a slow `handle`. Only a done `Subscribe` ctx ends a wait (`WithAutoUnsubscribe`), `Unsubscribe` does not. Recommended order is `Recover`, then `WrapError`, then `Retry`, then the user's, so `Recover` catches panics in every later middleware and its `*PanicError` is not wrapped, `Retry` and `IsRetryable` see `handle`'s raw errors, only the last one is wrapped, and panics are not retried. Middlewares have no effect on `SubscribeSeq` (the loop body is the caller's, and a recovered loop body panic cannot resume a range-over-func). The `discarding` check and `report` stay in `Consume`, outside the chain, so `Recover` never recovers a panic in an error handler. Tests: `middleware_test.go` (through a `Broadcastor`), `middleware/recover_test.go` and `middleware/wrap_error_test.go` (unit tests calling the wrapped handler directly, no synctest; the shared `failOn` handler and the `Recover` + `WrapError` test are in `middleware/middleware_test.go`) and `middleware/retry_test.go` (the same, but the ones that check waits run in a synctest bubble, whose fake clock makes the time between two calls exactly the wait). Other tests add `Recover` or `WrapError` only when they check a `*PanicError` or `*HandleError`, and otherwise check `handle`'s raw error (`recordFailures` matches the `handleError` type, wrapped or not).
- Options: `subscriber.Option[T]` (`WithBuffer`, `WithErrorHandler`, `WithMiddleware`, `WithAutoUnsubscribe`, `WithDefaultMessageOptions`, `WithDefaultUnsubscribeOptions`, `WithTimeout`, in `subscriber/options.go`) is applied in `subscriber.New` to an unexported `config[T]`, which `New` then builds the subscriber from (`buffer` sizes the channel). Options change only that config, never the subscriber itself: `id`, `ch`, `discarding`, `stopAutoUnsubscribe` and `refs` are set by the library. `subscriber.UnsubscribeOption` (`WithUnsubscribeDiscard`, `WithUnsubscribeDeliver`) is applied in `Subscriber.Unsubscribe`, see above. `WithMiddleware` does nothing for `SubscribeSeq`, whose loop body runs in the caller's goroutine. `message.Option[T]` (`WithSync`, `WithParallel`, `WithAsync`, `WithNonBlocking`, `WithErrorHandler`, `WithTimeout`, in `message/options.go`) set up the `message.Config` of the `message.Message[T]` (value + config) that a single `Broadcast` sends to one subscriber. Unlike `subscriber`'s `config`, `message.Config` and `message.Message` have exported fields, because `subscriber` reads them. That config is built **per subscriber** by `message.New`, called from `Deliver`: first a copy of `config.defaults` (filled in once by `subscriber.WithDefaultMessageOptions`), then the `Broadcast`'s options, which override it. `config[T]` is generic because of its `middlewares`. `message.Config` does not need `T`, so `message.Option[T]` keeps its type parameter only for the public API. Sync, parallel, async and non-blocking are a single `message.Config.Delivery` enum (`message.DeliverySync` is the zero value), so the last of those options wins. A subscriber whose default is `message.WithAsync` or `message.WithNonBlocking` is never waited for, unless a `Broadcast` passes `message.WithSync`. `subscriber.WithTimeout(d)` is just shorthand for a default `message.WithTimeout(d)`, so a `Broadcast`'s own timeout replaces it (0 means none). The `ctx` of `Unsubscribe` is unused.
- Errors are typed structs, each with an exported `SubscriberID`: `*SubscriberNotFoundError` in `errors.go`, and `*subscriber.HandleError[T]`, `*subscriber.PanicError[T]`, `*subscriber.TimeoutError[T]`, `*subscriber.DroppedError[T]` and `*subscriber.ClosedError[T]` in `subscriber/errors.go`. Every type the library creates (all but `HandleError`, which `middleware.WrapError` makes to wrap the user's error) has an `Is` method matching one sentinel (`ErrSubscriberNotFound` in `broadcastor`; `ErrPanic`, `ErrTimeout`, `ErrDropped` and `ErrClosed` in `subscriber`), so callers can use `errors.Is` without knowing `T`. `TimeoutError` also unwraps to the ctx error, and `PanicError` to the panic value when that is an error. `broadcastor.ErrClosed` has no type: `Subscribe`, `SubscribeSeq` and every `Close` after the first return it as is. It is a different sentinel from `subscriber.ErrClosed`, which `*subscriber.ClosedError` matches.

## Tests

Tests live in the root package (`broadcastor_test`), including those of what lives in `subscriber` and `message`: they go through a `Broadcastor` and share its helpers, so `subscriber` and `message` have no test files of their own. A test is named after the option it covers, package included (`TestSubscriberWithBuffer`, `TestMessageWithAsync`).

Most tests run inside a `synctest` bubble. There, a subscriber goroutine that never ends (because its channel was never closed, or because it is stuck) fails the test, and `synctest.Wait()` after `Unsubscribe` waits until the subscriber has processed everything. Every wait is bounded by `deadlockTimeout`, so a deadlock fails the test instead of hanging. `pkg/gate`'s tests run in real time instead: a goroutine blocked on a `sync.RWMutex` is not durably blocked, so `synctest.Wait()` would hang while `Close` waits for `Leave`.

The examples (`examples/NN-name/main.go`, numbered from simple to complex, listed in the README) are `main` programs, each with a `main_test.go` whose `Example()` runs `main()` and checks its output. They run in real time, not in a bubble, so their output must not depend on scheduling: they synchronise on channels or a `WaitGroup`, or use `// Unordered output:`. A slow `handle` waits on a `release` channel rather than sleeping. `forbidigo` is excluded for `examples/` in `.golangci.yml`, since they print. `bench_test.go` holds the benchmarks. Each `BenchmarkBroadcast` op waits until every subscriber has handled the message, which keeps async from piling up goroutines.
